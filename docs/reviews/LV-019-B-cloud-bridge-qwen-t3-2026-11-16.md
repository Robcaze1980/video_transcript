# LV-019.B - Architecture review: Hosting -> public gateway -> private Cloud Run

Date 2026-11-16. Repo `Robcaze1980/video_transcript`, HEAD `df96e12`. Review only; no code, deploy, IAM or ingress changes. Scope: Hosting rewrites `/api/video/*` to a new public Cloud Run gateway that verifies Firebase ID tokens, allows fixed paths/methods/body sizes, disables caching, and forwards over VPC to the internal files/AI service using `X-Serverless-Authorization` with a Google-signed ID token while preserving the Firebase bearer for backend ownership checks.

## Verdict

The shape is sound and consistent with repo constraints: the private service stays `INGRESS_TRAFFIC_INTERNAL_ONLY` with IAM enforced (`deploy/google-cloud/files.plan.json`; drift guards `deploy/google-cloud/files-deploy.mjs:101-106`, `deploy/google-cloud/ai-deploy.mjs:93-106`), and Hosting's official Cloud Run rewrite path expects unauthenticated invocation, so rejecting the direct rewrite to the private service is correct. The public account API (`deploy/google-cloud/account.plan.json`, `INGRESS_TRAFFIC_ALL` + `allUsers` invoker + app-level Firebase verification) already proves the same-origin rewrite pattern this design extends. Three material corrections/missing gates must land in the spec before implementation.

## 1. Gateway egress to the private service is unproven; make it a deployment gate

Nothing in the repo gives an HTTP service that internal route today. In `deploy/google-cloud/files.plan.json` only the `proof` job has `vpcAccess` (Direct VPC, `vistavo-private`/`vistavo-us-central1`, `ALL_TRAFFIC`); both services deploy without a VPC field (`files-deploy.mjs:102`). Cloud Run `internal` ingress does not admit another Cloud Run service via the public `run.app` URL without an internal path; the plan's own notes record the working pattern: Direct VPC `ALL_TRAFFIC` + Private Google Access on the existing subnet, no NAT/ALB. Required gates: (a) gateway spec pins Direct VPC egress `ALL_TRAFFIC` on `vistavo-private` with PGA; (b) minted IAM ID token audience equals the exact private service URL; (c) pre-promotion proof: call succeeds through VPC and the same call over public egress is rejected. Pin `invokerIamDisabled:false`, reject `allUsers`/`allAuthenticatedUsers` on the private service policy (mirroring existing drift guards), and grant the new gateway SA `roles/run.invoker` on `vistavo-files-api` only, with no Firestore/GCS/secret roles.

## 2. Path/header/body contract must match the real backend handlers

- Prefix mapping: the backend matches absolute `/api/cloud/...` paths (`server/commercial/firestoreHttp.ts:65-109`; `firestoreAiHttp.ts:5` requires `/api/cloud/ai/`). Hosting preserves the source path, so the gateway must translate `/api/video/*` -> `/api/cloud/*` with a fixed table, 404 on anything unmapped; no blind prefix strip. The local proxy models this discipline (`server/commercial/isolatedCandidateProxy.ts:36-47`: exact method+route allowlist, bounded header forwarding).
- Header allowlist must be semantic: besides `Authorization` (Firebase bearer passthrough), `Content-Type`, `Accept`, downloads/review need `Range`, `If-Range` and the `download=1` query (`firestoreHttp.ts:89-105`; `firestoreAiHttp.ts:28` derives `Content-Disposition` from it); chunk append needs the `offset` query. Strip client-supplied `X-Serverless-Authorization` and hop-by-hop headers before injecting the gateway token; cap header size (backend caps bearer at 7000 chars, `firestoreHttp.ts:58`).
- Body caps must equal backend limits or valid traffic breaks: JSON 400000 bytes (`firestoreHttp.ts:17`), upload chunks 8 MiB (`server/commercial/privateObjectPlan.ts:4`, enforced at `firestoreHttp.ts:77-81`). A generic small fixed cap would 413 every chunk PUT. Stream bodies duplex; never buffer whole videos in the gateway.
- Origin and identity: backend 403s any `Origin` other than `https://vistavo.app` (`firestoreHttp.ts:55`); same-origin browser requests pass through Hosting, so forward Origin unchanged. The gateway must independently enforce `verifyIdToken(token,true)` (revocation) plus `email_verified` (`firestoreHttp.ts:59-61`, `firebaseAccess.ts:40`); its checks never replace backend verification or UID-derived ownership (`accountForUid`).

## 3. Hosting CSP/rewrite guards are missing gates for the new surface

- The published commercial config has no `/api/video` rewrite and a global CSP `connect-src 'none'` (`firebase.commercial.json`); as shipped, the browser cannot call the new API. The account precedent shows the per-route deltas: rewrite plus route-scoped `Cache-Control: private, no-store` and `Vary: Authorization` (`scripts/publicAuthAssets.mjs:6`), because global `**` headers set `public,max-age=0,must-revalidate`. Spec must add a scoped CSP override (`connect-src 'self'` + Firebase Auth/securetoken origins) only on pages that need it, without weakening the marketing CSP.
- An executable guard currently rejects any non-account rewrite (`scripts/publicAuthAssets.mjs:8` `assertAccountHosting`; `server/commercial/publicAuthExport.test.ts:16` explicitly throws on a `/api/**` rewrite to `vistavo-files-api`). Extend that guard and its tests deliberately to accept exactly the gateway rewrite (never the private service) before deploy; loosening it silently would erase a safety invariant.
- 60 s Hosting limit vs 300 s backend service timeout (`files.plan.json` services.api): every gateway route must finish well under 60 s. Chunked upload (8 MiB PUTs) and ranged/streamed downloads already comply (`firestoreHttp.ts:102-105` streams beyond the 30 MiB buffered limit); long AI work stays async via the existing job/outbox contract. Negative gate: no synchronous route proxies long operations; client retries stay idempotent (`requestKey`, offset/409) across gateway timeouts.

## Limits

- Identity domains stay separate (`docs/specs/LV-019-B-video-text.md`): the gateway serves the files/AI backend only, never `vistavo-account-api` or `vistavo-live`; UID->accountId mapping stays inside each backend.
- Static inspection only: no live IAM/ingress readback, no deployed gateway, no browser E2E. Prior `qwen-bridge-review.md` was INCONCLUYENTE (no repo access); this review is grounded in the cited files. PASS means the design is acceptable to specify with the three gates; it authorizes no deploy, IAM change, provider call, pricing or publication (Rob's decisions and existing LV-019.B gates stand).
