## Implementación candidata

- `gcsObjects.ts` implementa el JSON API de GCS con bucket y prefijo fijos, credencial de servidor, creación condicional y generaciones conservadas como cadenas. No entrega URLs de escritura ni sesiones GCS al navegador.

### Cadena causal del índice equivocado

El aplicador anterior consultó el listado de índices con una URL de collection group, pero la respuesta administrativa observada incluía índices de otras colecciones. Su matcher comparaba únicamente `queryScope` y campos, sin comprobar el collection group del nombre de recurso. Como outbox y fileOutbox usan `state + nextAttemptAt`, confundió el índice existente de outbox con el que necesitaba fileOutbox. Por eso el antiguo mensaje de cinco índices READY y foundation completa era una conclusión incorrecta.

El diagnóstico mediante el SDK nativo, `native-query-diagnose.mjs`, separó los casos: uploads funcionaba y fileOutbox devolvía código 9 con “requires an index”. El defecto no se descubría en el emulador ni con una mera comparación de campos del listado administrativo. El servicio de mantenimiento alcanzaba 503 y no podía completar el despacho durable necesario para purgar el fixture vencido.

Se corrigieron **ambos matches** del aplicador: el nombre debe empezar por `projects/vistavo-prod/databases/(default)/collectionGroups/<colección>/indexes/`, además de coincidir campos y scope. La función extraída `deploy/google-cloud/indexContract.mjs` tiene una regresión negativa que rechaza un índice hermano de campos idénticos; `index-contract-test.log` informa un caso aprobado. No se añadieron reintentos para convertir código 9 en éxito.

Después se creó el índice real de fileOutbox. `native-query-after-fix.log` muestra ambas consultas nativas aprobadas, con un documento en uploads y uno en fileOutbox. Esa lectura por sí sola sólo demuestra la corrección de las consultas. La purga se acreditó posteriormente mediante el follow-up y el readback descritos abajo. `foundation-index-scope-fix.log` conserva el nuevo índice inicialmente CREATING, sin confundir esa etapa con READY.

### Scheduler: fallos del controlador separados del proof

El primer controlador intentó forzar un Scheduler PAUSED y recibió HTTP 400 `FAILED_PRECONDITION`; ese fallo local se conserva en sus logs. Una variante que reanudaba, forzaba y pausaba inmediatamente podía impedir la entrega asíncrona. Se corrigió el procedimiento para reanudar el Scheduler exacto y dejarlo habilitado hasta observar la entrega real. Esa entrega alcanzó mantenimiento, que seguía respondiendo 503 por el índice ausente. No se atribuye todo el fallo a Scheduler ni se presenta el intento local fallido como un fallo distinto de los 24 controles ya aprobados.

Tras reparar el índice se solicitó otra ejecución real de mantenimiento; `scheduler-after-index-fix.log` registra la solicitud. La continuación confirmó después la purga efectiva. Scheduler queda habilitado con cron de cinco minutos hacia mantenimiento HTTP privado, mínimo cero; no ejecuta un Job de cómputo ocioso en cada tick.
