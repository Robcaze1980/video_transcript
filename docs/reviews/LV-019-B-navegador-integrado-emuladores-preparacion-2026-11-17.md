**Estado al 18 nov 2026: preparado para revisión; historia integrada no ejecutada.** No se ha generado manifiesto, iniciado el navegador o modificado ningún emulador para esta historia. Los controles unitarios de guardas usan solo servidores propios temporales. La función real de revisión continúa apagada y el adaptador no se registra en el runtime publicado.

## Alcance propuesto

Un navegador aislado abre, mediante un único servidor HTTP de loopback, el editor de la candidata y el `firestoreHttp` real. El router llama al adaptador de frases y al servicio Firestore reales. Un primer bundle de prueba conserva el selector normal en `false` y comprueba que no aparece el editor ni se solicita su API. Un segundo bundle, **solo de esta prueba**, sustituye el selector fijo para activarlo. Ambos sustituyen el adaptador de acceso del navegador por otro que usa Firebase Authentication Emulator.

Dos usuarios de Auth Emulator se crean con identificadores y contraseñas inventados, para validar el token con Firebase Admin y comprobar separación de cuentas. La raíz propia de Firestore Emulator recibe un video y artefactos inventados; las lecturas de objetos se hacen desde un `Map` en memoria, no desde GCS. Se crea una captura **simulada** y un recibo de proveedor marcado como sintético, sin llamadas de IA ni pagos. El video de entrada se precarga en el emulador: esta prueba no verifica su subida ni su procesamiento.

La historia propuesta comprueba: entrada del propietario, carga de frases, edición, guardado y reapertura autorizados, descarga efectiva de TXT/SRT a una carpeta temporal propia con contenido y tiempos exactos, rechazo de token inválido y del segundo usuario, y denegación tras retirar el video mediante el handler real. La web y su API comparten origen; las solicitudes de autenticación van al Auth Emulator de loopback, que es otro origen local. También compara el saldo y el número de recibos sintéticos antes y después de revisar y descargar.

## Aislamiento y limpieza

- Proyecto exclusivamente `demo-vistavo-review-browser`, Firestore `127.0.0.1:18765` y Auth Emulator `127.0.0.1:18766`; hub, logging y websocket usan 18767, 18768 y 18769. Son distintos de los emuladores compartidos. No usar ningún proyecto, token, cuenta o almacenamiento de clientes.
- El lanzador y el proceso hijo reciben una lista cerrada de variables y perfiles `APPDATA`, `LOCALAPPDATA` y `USERPROFILE` nuevos, dentro de carpetas únicas. Windows puede agregar `HOMEDRIVE`/`HOMEPATH` del usuario aunque se envíe un ambiente mínimo: ambos se establecen expresamente hacia el perfil sintético, junto con nombre/dominio de proceso sintéticos. No se copia ni lee ADC real. El lanzador rechaza un ambiente no limpio **antes** de cargar el plugin de compilación; debe iniciarse desde un proceso padre limpio, pues `NODE_OPTIONS` puede ejecutarse antes de cualquier comprobación dentro de Node.
- El guard del proceso Node solo permite conexiones de salida a los dos puertos dedicados, fuerza redirecciones fallidas y proporciona un atestado comprobado por la fixture antes de usar los emuladores. Las pruebas aisladas comprobaron dos redirecciones sin solicitudes al destino y rechazo de puertos compartidos. El guard no es una frontera contra un proceso malicioso del mismo usuario.
- Chrome se inicia como proceso hijo oculto con perfil propio y CDP por pipe, sin puerto de depuración. El servidor web escucha solo en una dirección loopback y puerto efímero. Las peticiones de la página se interceptan y solo se autorizan la web local y Auth Emulator. Además, un proxy local rechaza conexiones no locales y se desactivan funciones de red de fondo.
- **Límite de red:** el guard de Node y la interceptación de página no son un cortafuegos del sistema. Esbuild, Chrome y dependencias nativas no quedan completamente cubiertos; no debe afirmarse aislamiento absoluto de red solo por estas guardas. Antes de ejecutar, revisar si hace falta un aislamiento independiente de red compatible con mantener ambos emuladores locales disponibles.
- Un inventario `synthetic-resources.ndjson` se escribe y sincroniza **antes** de crear la raíz, cada usuario y Chrome. Guarda UUID, correo inventado y marcador, nunca contraseña ni token. La raíz Firestore usa una colección fija de ensayo; solo se borra esa raíz tras verificar su marcador y después se comprueban su ausencia y la de sus descendientes. Los usuarios se borran individualmente solo tras confirmar UID, correo sintético y marcador; se verifica que ya no existan. La comprobación y el borrado de Auth no son atómicos: los emuladores deben ser exclusivos de la prueba, sin escritores simultáneos.
- Antes de borrar, se rechazan solicitudes nuevas y se espera a que finalicen las promesas de los handlers, además de cerrar el navegador propio. Si no se confirma el drenaje o cambia la identidad de los emuladores, se conserva el inventario y se omite la limpieza externa. Un archivo parcialmente borrado o una respuesta perdida no autorizan ampliar el borrado.
- Si la creación no se confirma, falta un marcador, una limpieza falla o se interrumpe el proceso, no se declara limpieza verificada ni se borran otras raíces o usuarios. El lanzador registra el PID y el perfil del Chrome propio; si el hijo se interrumpe, se inspeccionan antes de cualquier limpieza manual. Nunca cerrar el Chrome normal del usuario.
- La presencia de un servidor en un puerto no identifica por sí sola al proceso del emulador. `--attest` comprueba que Auth sea el Node/Firebase CLI esperados, con el proyecto y configuración generados, que Firestore sea un Java descendiente con el JAR y puerto esperados y que no haya conexiones establecidas al comenzar. Se registra PID y fecha de inicio y se vuelve a comprobar antes, durante y después de la prueba. No es una autenticación criptográfica del socket y existe una ventana entre cada comprobación y una operación.
