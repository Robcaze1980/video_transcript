## 2. Verificación de controles específicos y descartes de Codex

1. **JSON Firebase `8192` + `catch` HTTP exterior (confirmado en código):** En `server/commercial/pilotHttp.ts`, `createFirebaseRoutes` recibe `req => jsonBody(req, 8192)` (no el default `4096`), suficiente para `idToken` de hasta 7000 caracteres más envoltura JSON; además, el `try/catch` exterior del handler HTTP en `pilotHttp.ts` captura `RequestError` (devolviendo `400` o `413`). No es defecto de código; mantener pruebas HTTP negativas con tokens límite en B3.
2. **Cuota de voz conserva bytes hasta `unlink` y `reconcile` borra filas (confirmado en código):** En `server/commercial/migrations/0016c_voice.sql`, `pipeline_voice_reserve` suma `reserved_bytes` sin excluir `released` y el trigger `pipeline_voice_tombstone_narration` retiene cuota deliberadamente hasta borrar el archivo físico. En `server/commercial/pipelineVoiceService.ts`, `reconcile()` ejecuta primero `this.files.remove(...)` y, sólo tras completar el borrado físico, elimina las filas en `pipeline_voice_reservations` y `pipeline_voice_tombstones`. No debe relajarse el SQL filtrando `released` antes del `unlink`; en Cloud Run deberá garantizarse un disparador durable para `reconcile()` (B4), no un `setInterval` dependiente de proceso activo.
3. **Loopback, proxy y pagos simulados como guardas locales a conservar (confirmado en código):** El bind `127.0.0.1` en `pilotHttp.ts`, la exigencia de PostgreSQL loopback en puerto no estándar en `pilotLocal.ts`, las restricciones de `privateOrigin` / `.ts.net` y el bloqueo de `textPipeline`/`voicePipeline` sin `payments.simulateApproval` son salvaguardas intencionales de entorno local (`AUD-05`). Deben conservarse para desarrollo local y construir por separado el entrypoint Cloud Run y adaptadores durables.
4. **Supabase legacy no es el login vigente (confirmado en código y snapshots):** `pilotLocal.ts` rechaza activar Firebase y Supabase a la vez; `accountAccess.sql` separa `commercial_supabase_identities` de `commercial_firebase_identities`; `inventory.json` no detecta claves de Supabase en los `.env*` inspeccionados y no existe proyecto Supabase alojado de Vistavo acreditado. Firebase Auth en `vistavo-prod` es el proveedor vigente y no hay migración a Supabase abierta.
5. **Sólo preview estática sin endpoint IA público acreditado (confirmado en snapshots):** `outputs/vistavo-a3-publish/acceptance.json` acredita `vistavo.app` (versión `98a81624fa93bb66`) como vista previa comercial `noindex` con logo A3 y backend deshabilitado. `backend-remote.json` y `inventory.json` confirman APIs Cloud Run Admin y Cloud SQL Admin deshabilitadas (`403`) y `0` buckets en Storage. Aunque existen rutas sin auth en `server/index.ts` y fallback directo `VITE_GEMINI_API_KEY` en `services/geminiClient.ts` (`AUD-04`), no hay exposición pública acreditada; ambos deben quedar excluidos del entrypoint y build comerciales.

## 3. Revisión transversal por superficie

- **Arquitectura:** Firebase Hosting + Auth (`vistavo-prod`), Cloud Run (Node 24 + FFmpeg), Cloud SQL PostgreSQL y Cloud Storage privado. Se conserva PostgreSQL (ledger y colas `SKIP LOCKED`) sin exigir rediseño a Firestore.
- **Esquemas y migraciones:** Existen `schema.sql` y migraciones aditivas aplicadas por `pilotLocal.ts`. Falta migrador cloud versionado, idempotente (instalación limpia y upgrades) y prueba de restauración aislada (B2).
- **Login y seguridad:** `firebaseAccess.ts` / `firebaseRoutes.ts` / `accountAccess.ts` implementan verificación de ID token y session cookie con `checkRevoked=true`, `email_verified=true`, control de `auth_time`, cookie `HttpOnly; SameSite=Lax`, comprobación de `Origin` y bloqueo `pg_advisory_xact_lock` por UID. Brechas abiertas (B3): `PeerLoginLimiter` en memoria por `remoteAddress` (vulnerable a agrupación tras proxy en Cloud Run y a multiplicación por réplica), `previewAttribution.ts` con clave `randomBytes(32)` por proceso y sin `Secure`, distinción explícita entre logout local (actual) y revocación global, y pruebas E2E reales en PC/Pixel con correo real. *Nota:* MFA deshabilitado (`backend-remote.json`) y ausencia de tope monetario duro se registran como decisiones de riesgo/coste del propietario, no como gates impuestos por esta auditoría.
- **Pagos y ledger:** `schema.sql` y `jobs.ts` garantizan `credited = available + reserved + consumed` y unicidad de captura/movimiento terminal (`one_terminal_movement`). Brechas (`AUD-06`): en `checkout.ts`, si falla la respuesta tras crear orden en PayPal, la fila queda con `provider_order_id = NULL` y `next_attempt_at = NULL` sin recuperación; `fulfillNext` reintenta cada 90 s sin estado terminal acotado para órdenes abandonadas/rechazadas; moneda `'USD'` fija en `createOrder` y dependencia estricta de `payee.merchant_id` deben validarse contra Sandbox real (PC/Pixel) y separar PayPal Live en B5/B6.
- **Cola, leases y `UNKNOWN`:**
  - `CommercialJobs` (`jobs.ts`): Codex reprodujo localmente en esquema efímero `AUD-01` (`expired-inline-proof.json`: input inline caducado invoca el adaptador 1 vez antes de fallar en `finish`) y `AUD-02` (`publish-replay-proof.json`: error tras éxito del adaptador deja el job `running` y tras expirar lease se ejecuta 2 veces, manteniendo 1 captura). Además (`AUD-03`/`AUD-09`), `runOnce` ignora errores de `renew` en heartbeat, `cancel` sólo aborta `activeAttempts` locales, no modela `unknown` ante timeout/red, un worker sin la clave de servicio falla el trabajo en rolling updates, y existe riesgo potencial de orden de locks entre `purgeExpiredInputs` y `finish` pendiente de reproducción.
  - `PipelineStore` (`pipelineStore.ts`): Diseño sólido (snapshots inmutables, fencing por `attempt_id`/lease, manifiestos `staged -> ready`, transición a `unknown` sin reintento automático). Detalle menor (`AUD-09`): `publishArtifact` en conflicto `ON CONFLICT` no actualiza `attempt_id` (latente porque `unknown` no reintenta el mismo job) y `deleteSubtitleProject` devuelve `true` aunque `removeTerminalArtifacts` no borre cuando haya un job legacy activo (`AUD-08`).
- **Almacenamiento durable:** `PrivateFileStore` + `ResumableUploads` operan sobre disco local con validación MP4/`ffprobe` endurecida (`-enable_drefs 0 -use_absolute_path 0`) y `append` idempotente (el `409` en offsets incompatibles no es corrupción). Brechas (B2/`AUD-05`/`AUD-08`): requiere adaptador GCS durable (sin montaje POSIX), límites `receivingUploads`/`finalizingUploads` fuera de memoria de proceso, corrección/ensayo de `abortWithClient` (unlink antes de commit) y prueba de borrado parcial/huérfanos.
- **Texto, voz, render y Drive:**
  - *Texto/Voz (`LV-016.B/C`):* Sin autorización de gasto/trial ni ledger (`AUD-07`), exclusivos del ensayo simulado. `geminiFileUpload.ts` no persiste tumba durable si falla `DELETE` (`AUD-08`); `pipelineTextTiming.ts` omite `-enable_drefs 0 -use_absolute_path 0` en `ffmpeg` (`AUD-09`); `transcriptionSession.ts` (cliente) reintenta errores de validación de cues hasta 3 veces. Aceptación humana de voz inglesa pendiente.
  - *Render (`LV-016.D`):* Contrato de DAG en `PipelineStore` y smoke Linux `deploy/google-cloud/probe` disponibles, pero render MP4 largo en servidor aún no implementado (B4/B5).
  - *Drive:* Implementación cliente separada de Firebase Auth (`driveAuthorization.ts`, `pilotDrive.js`), pendiente de consentimiento y E2E real en PC/Pixel (`AUD-10`).
- **Operación, coste y cobertura:** Cobertura documental acreditada (`review-packs.json`: 103 archivos únicos en paquetes `core`/`media`; `coverage-map.json`: 76 archivos auxiliares/frontend; `check-results.json`: reportado por Codex con Node v24.13.0, tipos `0`, 306 pruebas en 43 archivos sin omisiones y 2 builds en `0`, más las 2 pruebas sintéticas locales). Pendientes B1/B6: IaC reproducible con digest, Secret Manager/IAM mínimo, backups/PITR + restauración aislada, medición real de costes/egress/alertas, soporte/legales y revisión lingüística nativa.
