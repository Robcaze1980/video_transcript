# LV-019.B · Canon local de voz v1

**Estado:** componente puro, aislado y pendiente de auditoría; no conectado a reservas, red ni interfaz. Los [gates de voz](LV-019-B-voz-desde-revision.md) y la revisión T3 inconclusa siguen vigentes.

La entrada debe provenir de una transacción de confianza que haya comprobado por separado UID→cuenta, propiedad, input, trabajo de texto, captura y acceso. El componente no verifica esas condiciones ni acredita que documentos matemáticamente coherentes procedan de Firestore. Una prueba demuestra expresamente que un llamador que fabrica un par coherente puede satisfacer el cálculo. Tampoco autentica el proveedor, autoriza un cobro o cancela una solicitud enviada.

El módulo recibe IDs de cuenta, input, trabajo de texto, revisión y recibo; el `bindingHash` validado por el llamador; y las copias completas de ambos registros. Rechaza campos ausentes o futuros, accesores y tipos inconsistentes. Recalcula `reviewId = SHA-256(UTF-8(JSON.stringify(['review-revision-v1', accountId, inputId, textJobId, revision])))`, comprueba la referencia cruzada del recibo, los campos correlacionados y la revisión anterior. Exige igualdad de `createdAtMs`, coherente con el escritor actual que usa el mismo `now` para ambos documentos; esa igualdad no prueba procedencia ni una transacción real. El ID del recibo se comprueba contra el ID de documento que recibió y la referencia de la revisión; no se afirma que haya podido derivarse de la solicitud original, cuyo `requestKey` no está almacenado en ese recibo.

El payload debe ser el JSON exacto producido por `JSON.stringify` de ECMAScript, en el orden almacenado; su SHA-256 se calcula sobre UTF-8. Se vuelven a validar los IDs y tiempos de cues mediante el codec existente; después se reconstruye el texto con los textos ingleses ordenados, cada uno seguido por LF. Se recalculan el fingerprint de revisión y `voiceTextSha256`. Se rechazan textos de más de 12.000 unidades UTF-16, límite del proveedor candidato.

El divisor actual `narrationChunks` es parte de esta versión: recorta espacios exteriores, separa ciertas frases, separa palabras cuando la frase supera 320 unidades UTF-16 y puede unir separadores mediante un espacio ASCII. **No conserva todos los espacios ni saltos de línea del texto fuente.** No realiza normalización Unicode; los vectores incluyen acentos compuestos/descompuestos y caracteres suplementarios al límite. Esta regla describe el código actual y no demuestra calidad de pronunciación ni sincronización con el video.

Para cada ordinal `voice-chunk:NNNN`, `narration:en:female` selecciona `Kore` y `narration:en:male` selecciona `Charon`; ambos usan el modelo y estilo fijo existentes. El cuerpo se construye con el orden de propiedades de `JSON.stringify` usado por el proveedor candidato. Solo se acepta una cadena idéntica a ese cuerpo; `requestSha256` corresponde a sus bytes UTF-8 exactos. El resultado devuelve esa cadena inmutable, que contiene texto privado y **no debe registrarse**. El llamador futuro debe enviar esa misma cadena y revalidar el vínculo antes de cada admisión.

Los [vectores sintéticos](../../server/commercial/reviewedVoiceCanonical.vectors.json) fijan hashes y cuerpos para una revisión de dos cues, límites de 320 unidades ASCII y 160 símbolos suplementarios, un LF conservado y una secuencia combinante en el límite. Un [verificador independiente en Python](../../scripts/verifyReviewedVoiceVectors.py) contrasta los cinco vectores y ocho llamadas para el subconjunto de JSON y espacios que contienen, sin afirmar equivalencia general con ECMAScript. Las pruebas negativas cubren propietario/revisión/recibo, campos añadidos, hashes y texto alterados, JSON ambiguo, voz/modelo/estilo equivocados, límites y Unicode. La comparación de hashes no prueba procedencia ni elimina la necesidad de revisar los registros en la transacción que admite el trabajo.

El límite defensivo de 1.000 fragmentos no es alcanzable con el límite previo de 12.000 unidades y el divisor actual: cada par de fragmentos consecutivos producido por desbordamiento suma al menos 320 unidades, por lo que 1.001 fragmentos necesitarían al menos 160.000. El límite de 16 KiB del cuerpo también es defensivo: el texto de un fragmento cabe en 320 unidades UTF-16 y el resto del cuerpo es fijo. Esos límites no sustituyen las restricciones de duración o gasto.

Quedan pendientes los límites operativos de duración estimada, tamaño/costo de audio, tratamiento de texto que no quepa en el divisor, reproducibilidad entre runtimes y proveedores, calidad humana, retención y las carreras financieras. Una coincidencia de canon no afirma que el servicio de voz pueda ejecutarse, que el proveedor respete el texto ni que el servicio esté listo para producción.
